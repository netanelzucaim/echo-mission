# Compare Trivy and Grype scans: ranking and diagrams

Merge one Trivy JSON report and one Grype JSON report of the same image. The script produces three files, the same way for every image:

- `triage.md`: summary counts and the top of the ranking
- `triage.csv`: every vulnerability, ranked
- `stats.md`: the statistics as Mermaid diagrams and tables (renders on GitHub)

The ranking deliberately does not put "Critical in both scanners" first: a Critical finding in a library the main program never runs matters less than a High one in code every deployment executes.

## When to use

The user has (or wants) Trivy and Grype results for a container image and asks to compare them, decide what to fix first, or see the numbers as diagrams.

## Rule: diagrams come from the script

Never write the statistics diagrams by hand. They are generated by the script from the reports, so a different image, or a rescan, gets the same diagrams with its own numbers. If the user wants a new diagram or statistic, add it to `write_stats()` in `scripts/compare-scans.py` and rerun.

## Inputs

1. Two JSON reports of the same image:
   - Trivy: `trivy image --format json -o trivy.json IMAGE`
   - Grype: `grype IMAGE -o json > grype.json`
2. Optional but recommended, `linked-packages.txt`: the package of the image's main program plus the packages whose libraries it loads, one name per line. Replace the binary path with the image's main program:

```sh
docker run --rm --entrypoint "" IMAGE sh -c '
  { echo /usr/sbin/nginx; ldd /usr/sbin/nginx | awk "{for(i=1;i<=NF;i++) if (\$i ~ /^\//) print \$i}"; } |
  while read -r p; do
    r=$(readlink -f "$p")
    dpkg -S "$r" 2>/dev/null || dpkg -S "${r#/usr}" 2>/dev/null || dpkg -S "$p" 2>/dev/null
  done | cut -d: -f1 | sort -u' > linked-packages.txt
```

3. Optional, `modules.tsv`: for images with optional add-on packages (modules, plugins), one line per `module<TAB>package` naming the packages installed only because of that module. Replace the module package names:

```sh
docker run --rm --entrypoint "" IMAGE sh -c '
  only=$(apt-get -s remove --auto-remove "$@" 2>/dev/null | awk "/^Remv/ {print \$2}" | sort -u)
  for c in "$@"; do
    apt-cache depends --recurse --installed --no-recommends --no-suggests --no-conflicts \
      --no-breaks --no-replaces --no-enhances "$c" 2>/dev/null | grep -v "^ " | grep -v "^<" | sort -u |
    while read -r p; do
      [ "$p" = "$c" ] && continue
      if echo "$only" | grep -qx "$p"; then printf "%s\t%s\n" "$c" "$p"; fi
    done
  done' sh MODULE_PACKAGE_1 MODULE_PACKAGE_2 > modules.tsv
```

Both snippets are for Debian/Ubuntu images. On other distributions use the matching package queries. Without these files the script still runs; it warns, and the "where the vulnerabilities live" and "optional modules" parts of `stats.md` are left out.

If only table/text reports exist, ask for JSON or rerun the scans; do not parse the text tables. If the two reports come from different images or digests, say so before comparing.

## Keep the output folder tidy

Do not pile everything into one folder. Use this layout, and pass `--out-dir` so the three result files land at the top:

```
scans/<name>/
  stats.md, triage.md, triage.csv   results, read these
  reports/                          trivy.json, grype.json (raw scanner output)
  image/                            linked-packages.txt, modules.tsv (facts about the image)
```

## Steps

1. Find the two JSON reports (commonly `scans/<name>/reports/trivy.json` and `grype.json` beside it). Ask if they cannot be found.
2. Make sure `linked-packages.txt` and, where the image has optional modules, `modules.tsv` exist in the scan's `image/` folder. `scripts/scan-baseline.sh` (`make scan-baseline`, with `IMAGE` and `OUT` for another image) writes both; the snippets above are for doing it by hand.
3. Use `scripts/compare-scans.py` from this repository. For the baseline, `make triage` runs it with the right arguments.
4. Run, with `--out-dir scans/<name>` when using the layout above: `python3 scripts/compare-scans.py TRIVY_JSON GRYPE_JSON [--linked FILE] [--modules FILE] [--out-dir DIR] [--top N]`. It needs only the Python 3 standard library.
5. Read `triage.md` and `stats.md` and report to the user, in this order:
   - the top of the ranking, with score, whether the main program loads the library, and whether a fix exists;
   - anything known exploited (KEV) or with a high EPSS that ranks low only because the main program does not load it;
   - the headline counts, and where the diagrams are (`stats.md`);
   - for the top few, read the advisory text and say whether the main program actually calls the vulnerable function. The score cannot know this.
6. Point to `triage.csv` for the full list. Do not paste hundreds of rows or re-draw the diagrams in the reply.

## What `stats.md` contains

A breakdown flowchart (scanners, agreement, where the CVEs sit, how many have a fix); pies for where the vulnerabilities live, loaded packages, highest severity, scanner agreement and fix availability; tables for findings per scanner, exploitation signals (KEV, EPSS), optional modules and the packages with the most CVEs.

## How the score works

`score = 100 x danger x reach`

- **Danger (0 to 1)** = 0.6 x exploitation + 0.4 x severity.
  - Exploitation is 1.0 if the CVE is in CISA's Known Exploited list, otherwise its EPSS probability.
  - Severity is the average of the two scanners' ratings (Critical 1, High 0.75, Medium 0.5, Low 0.25). A scanner that does not report the CVE counts as 0, so agreement raises the score.
- **Reach (0 to 1)** comes from a reviewed verdict in `review.tsv`, or a default by where the package sits. The verdicts, weights and how to review are in the `triage-cves` skill.

Ties are broken by fix available, then CVSS.

## Packages not from the distribution

`triage.md` has a section listing installed packages that the distribution did not build (from `image/foreign-packages.tsv`). For those, the scanner results in this ranking cannot be trusted, because the scanners compare them with the distribution's version numbers. Their CVEs have to be added from the upstream project's advisories through `review.tsv`. The script prints a WARNING while that has not been done. The rule and the steps are in the `triage-cves` skill.

## Caveats to tell the user

- "Loaded" means the library is loaded by the main program, not that the vulnerable function is called. Confirm from the advisory before saying the program is affected.
- Both scanners match on package name and version; they do not inspect code. A package missing from both reports is not proven safe. Software installed from a non-distro repository (for example nginx from nginx.org on Debian) is compared against the distro's fixed versions and can be wrongly reported as clean, so its own CVEs may not appear at all.
- A scanner can also over-report: a KEV-listed CVE against the main program can top the ranking even though the shipped version already contains the upstream mitigation. Check the changelog before calling it open.
- EPSS and KEV describe exploitation anywhere, in any software using the library, not in this image.
- The weights (0.6/0.4, 1.0/0.4) are a judgment call. If the user wants a different emphasis, change the constants in the script and say what was changed.
- "Fix available" means a fixed package version exists, not that it has been applied.

## Where the script lives

The script is `scripts/compare-scans.py` in this repository. This skill does not carry a copy, so there is one version to maintain. `scripts/CLAUDE.md` describes its options and the scoring.
